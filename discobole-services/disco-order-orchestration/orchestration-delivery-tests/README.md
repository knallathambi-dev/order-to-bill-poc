# orchestration-delivery-tests

This is the Customer Order Orchestration & Distribution (COOD) APIs testing requests material to be used with [Bruno](https://docs.usebruno.com/introduction/what-is-bruno) for the DISCOBOLE Suite.

## Community

You can chat with the core team on [![Discord](https://dcbadge.limes.pink/api/server/pzcwfgqns7?style=flat)](https://discord.gg/pzcwfgqns7).

## Getting Started

Those COOD tests are running locally and remotely on **review** environment only becouse we are using mocked order IDs and order item IDs for the offers sent to the productOrder topic, along with mocked CPIB and catalog responses. However, in the integration environment, real data must be generated by the OM component, and the CPIB must also contain actual data. This is why we cannot use the test endpoint to publish events in the integration environment.

### Prerequisites

To run those COOD tests **locally**, you should follow those **main steps**:

1. [Download Bruno](https://www.usebruno.com/downloads) depending on your OS.

2. Install Bruno (example for Linux):

    ```bash
    sudo apt update
    sudo apt install bruno
    ```

    Nota: the version of Bruno should be equal or greater than `v1.28.0`.

3. Install `Nodejs` and `npm` (example for Linux):

    ```bash
    sudo apt install -y nodejs
    ```

    ```bash
    sudo apt install -y npm
    ```

    Nota: also `nvm`, the Node Version Manager, could be installed if you managed many `npm` versions: see [here](https://www.linode.com/docs/guides/how-to-install-use-node-version-manager-nvm/#use-nvm-to-install-node).

4. Install globally [Bruno CLI](https://docs.usebruno.com/bru-cli/overview) with `npm`:

    ```bash
    npm install -g @usebruno/cli
    ```
5. Setting Up the Review Environment for Tests
   - Make sure the mock server is running.  
     Verify that the mocks are installed from this repository: [mock-server](https://gitlab.tech.orange/disco/disco-oda-components/disco-order-management/mock-server).
   - Make sure COOD services are running.
     You can find the necessary setup in this repository: [orchestration-delivery-repo](https://gitlab.tech.orange/disco/disco-oda-components/disco-order-orchestration/orchestration-delivery) and [delivery-management](https://gitlab.tech.orange/disco/disco-oda-components/disco-order-orchestration/orchestration-delivery-management)
 
### Installing

To install **locally** this project, please follow this step:

```bash
cd <your_custom_directory>
git clone https://gitlab.ow2.org/discobole/disco-oda-components/disco-order-orchestration/orchestration-delivery-tests.git
```

## Environments

This orchestration delivery tests only supports the `review` environment.

## Running the tests

### Locally

1. Navigate to the directory where your API collection resides, and open CMD then run the following command:

    ```bash
    bru run --env review --insecure
    ```

    you can select to run specific folder inside the collection with the following command:

    ```bash
    bru run -r <specific folder>  --env review --insecure
    ```

2. You can also run the project using bruno tool with the following steps
     a. open Bruno GUI
     b. open the bruno collection project from <your_custom_directory>
     c. select the `review` environment
     e. run the collection (or select a specific folder inside the collection)

1. At the end of the run, a `report.html` with the results of those COOD tests should be generated on the **same folder**, and you can open it with your favorite browser (firefox for instance):

    ```bash
    firefox report.html
    ```

    Just browse the report clicking the requests and folders you want, to expand them to see more details.

 ### Running Tests Remotely

You can execute the Bruno tests directly from the CI/CD pipeline:

1. **Run the entire collection**  
   - Go to the [pipeline](../../pipelines/new) and click on **"New pipeline"**.  
   - This will execute all available Bruno test plans.  

2. **Run a specific folder in the collection**  
   - Define a pipeline variable with:  
     - **Key**: `BRUNO_FOLDER`  
     - **Value**: the name of one of the folders listed below  

`$BRUNO_FOLDER`  
- **Purpose**: Specifies which folder in the Bruno collection should be executed.  
- **Usage**: Set the variable value to the folder name that matches the type of test plans you want to run.  

#### Available Folder Values

| **Folder Name**                 | **Description**                                                                 |
|---------------------------------|---------------------------------------------------------------------------------|
| `Post_Requests_For_Acquisition` | Acquisition test plans mocked in the review environment                         |
| `Post_Requests_For_Migration`   | Migration test plans mocked in the review environment                           |
| `Post_Requests_For_Modification`| Modification test plans mocked in the review environment                        |
| `Post_Requests_For_NoChange`    | No-Change test plans mocked in the review environment                           |
| `Post_Requests_For_Termination` | Termination test plans mocked in the review environment                         |

---

> 💡 **Tip**: Use `BRUNO_FOLDER` when you only want to execute a subset of tests (e.g., only **Migration** or **Termination**), instead of running the entire collection.

3. let GitLab automatically trigger the pipeline whenever code is pushed, after any commit or a merge request is created, or run yourself the pipeline on demand.

4. the pipeline job artifacts will contain report.html.
You can download it from the pipeline job summary page under the Artifacts section.

5. How to Read the Report

The report shows a summary of all executed requests and tests.

- Total requests → number of requests executed

- Total errors → number of requests that returned errors

- Total controls → number of validation checks/assertions performed

- Total failed controls → number of validations that failed

- Run duration → total time of execution

Each request includes:
- ✅ Passed requests/assertions are shown in green.

- ❌ Failed requests/assertions are shown in red, with error messages available for debugging

💡 Tip: Always check failed assertions first, as they usually indicate mismatches between expected and actual responses.
